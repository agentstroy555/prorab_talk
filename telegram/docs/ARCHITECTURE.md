# Актуальная архитектура v0.3.7 build 15

Production Render Free использует PostgresStore и схему telegram в Neon.
Engine и STT/runtime ожидают асинхронные операции хранилища. SQLite остаётся
локальным тестовым адаптером; она не хранит production-данные на Render.
Webhook подтверждает приём только после commit; PostgreSQL advisory xact lock
сериализует queue admission, бюджет и изменения черновиков через pooler.
Общий lease допускает одного worker. При rolling deploy standby принимает
webhook в общую очередь и ждёт освобождения/истечения lease.
Render webhook автоматически регистрируется после открытия listener; секрет
стабилен, вычисляется из токена, pending updates не сбрасываются.
Web-таблицы остаются в public; web и bot не синхронизируют сами сметы.

# Архитектура Telegram MVP

## Поток данных

Telegram update → проверка private chat и Telegram identity → durable inbox (SQLite, unique update_id) → один последовательный worker → voice job/скачивание OGG → кэш/бюджет → Groq → parser/matcher → transaction строки и outbox → Telegram card.

Текстовые команды не требуют STT. Исходная запись скачивается в ограниченный по размеру буфер и после обработки не сохраняется на диск; остаются Telegram file_id, текст и структурированные поля. Для уточнения reply_to_message сопоставляется с доставленной карточкой из outbox. Нельзя уточнять строку другого сотрудника/сметы.

## Хранение

`src/store.js`: SQLite, WAL, foreign keys, prepared statements. Схема v2 (добавлена source_parts с backfill старых source_update, строки v1 сохраняются). Один сервис и одна реплика на постоянном диске. SQLite выбран для отдельного автономного MVP без внешних зависимостей; **это технический выбор реализации, а не требование навсегда отказаться от PostgreSQL**. Для нескольких реплик или хостинга без постоянного диска понадобится PostgreSQL и очередь с leases — до такого развёртывания, а не после потери данных.

Inbox и outbox сохраняются отдельно. Мутация строки, создание ответов и отметка inbox.done коммитятся атомарно. Голосовая работа предварительно сохраняет строку и job; распознанный текст сохраняется до финального применения. Recovery использует уже записанный transcript/cache. Смена товара удаляет выбранный SKU; правка текста полностью переразбирает поля; inline-кнопки проверяют revision.

С build 11 web и bot используют один процесс/HTTP listener, общий каталог и корневые parser/matcher/voice-utils без копирования. Общий запуск — src/service.js. Web PostgreSQL и Telegram SQLite остаются отдельными хранилищами. Поверх parser добавлены консервативные проверки: не выбирать «10 кг» по «10 литров», не использовать единственное голое число одновременно для SKU и количества, слабый family score не предвыбирать. Остальные ограничения baseline parser сохраняются: например, «тысяча штук», «тонна», «куб» не полностью покрыты. Ручной ввод всегда доступен. Состав SKU не выдумывается: в текущем каталоге Rotband 25 кг отсутствует.

## Доставка и сбои

Telegram updates повторяются: unique update_id предотвращает повторные строки и обычные повторные STT-запросы. Long polling сохраняет принятый batch до изменения offset. При переполнении batch откатывается; webhook отвечает 503. Порядок worker — по update_id среди уже принятых. В webhook при регистрации использовать max_connections=1, чтобы снизить перестановки входящих обновлений. Отсутствующие updates не угадываются.

**Exactly-once внешних API не обещается.** Если процесс погиб после отправки STT, но до сохранения ответа, ledger остаётся started/uncertain. Такой запрос не воспроизводится автоматически: строка остаётся с ошибкой, сотрудник выбирает `/retry ID` либо ручной текст. Кэш одинакового аудио повторно использует результат, но одинаковое сообщение, намеренно отправленное новым update, всё равно создаёт новую строку.

После неизвестного результата Telegram send ответ получает статус uncertain и автоматически не пересылается. Пользователь может запросить `/list`, `/row ID`, `/export`. Только определённый 429 повторяется с Retry-After и ограничением попыток. Логи содержат IDs, коды и статусы, без URL с токеном и без расшифрованных текстов.

Lease в БД не допускает два worker на одном диске. После аварийного завершения lease освобождается максимум через 60 секунд. Это не поддержка нескольких независимых SQLite-дисков для одного бота. graceful shutdown прекращает новые итерации и ждёт текущие bounded API операции.

## STT и ограничения

У отправленной Telegram voice-записи уже есть явная граница. Она считается намеренным пользовательским вводом, без Silero gate. Одно STT-распознавание всего сообщения затем локально делится на одну или несколько позиций. Ограничены duration (по Telegram metadata), bytes, STT requests/min/day, суммарные объявленные audio seconds/day. Неполученные/ошибочные/неопределённые попытки учитываются консервативно. Квота хранится в БД, выдерживает рестарт; календарный день квоты — UTC.

Groq допускает OGG; лишняя конвертация/FFmpeg сейчас не нужна. Перед отправкой проверяется OggS-сигнатура и потоковый лимит размера. **Это не полное декодирование или доказательство речевого содержимого**. Кашель может попасть в STT и дать неточный текст: известных hallucinations-фильтр ограничен и не заменяет корпусное тестирование. Слишком длинное голосовое отклоняется с объяснением, не режется на несколько строк.

STT timeout — 45 секунд. Есть общий cooldown по 429. Не выполняются неявные повторные STT попытки. `/retry` ограничен тремя повторами и тем же общим бюджетом. Ручное подтверждение отправки не обходит квоты. Значения defaults — консервативные настройки MVP, а не обещание совпасть с тарифом конкретного Groq-аккаунта.

## Ограничения первой реализации

- Один worker обслуживает всех сотрудников последовательно: длинный STT задерживает следующие команды. Это сохраняет порядок и упрощает надёжность малой команды; для роста нужна durable очередь по сотрудникам с общим лимитером.
- Максимум 200 строк на смету, 50 строк на одно сообщение, 12000 символов суммарно и 2000 на текст строки. Новые входящие ограничены длиной очереди.
- Входящие Telegram updates хранятся на стороне Telegram ограниченное время; долгий offline сервиса не равен надёжному архиву.
- Combined /api/health и /health проверяют PostgreSQL и готовность worker, но не качество STT или доступность внешних API.
- Автоматической очистки истории/кэша и бизнес-аудита пока нет; сроки хранения нужно согласовать перед регулярной эксплуатацией. Хранилище содержит рабочие тексты, требует закрытого доступа и backups.
- Цены, поставщики, руководительское согласование, группы, мультитенантность и коммерческий billing отсутствуют.
- Настоящие Telegram API, реальное аудио/Groq и Render после интеграции ещё не проверены.

## Разделение позиций в build 9

`src/splitter.js` использует явные переносы/точки с запятой/голосовые маркеры, а для обычного перечисления — названия из каталога и завершённое количество предыдущего товара. Размеры и фасовки не являются самостоятельными позициями. Неизвестные товары поддерживаются при явных границах; без них возможна склейка, для неё есть `/split`. Дополнительной LLM/STT-операции нет.

`Engine.addParts` в одной транзакции создаёт все строки, source_parts и ответы. При recovery/retry не создаются дубликаты; полный transcript хранится отдельно. source_update остаётся уникальным у первой строки, source_parts связывает сообщение с первой и остальными. `/split` сохраняет ID первой строки и вставляет новые перед следующими строками. Это не меняет смысл `/clarify`/reply: уточнение относится к одной карточке.

Паузы без данных о времени в STT json не анализируются. Алгоритм локальный и эвристический; не заявлять универсальную точность сегментации либо измеренное качество на реальном аудио.

## Публичный доступ с build 12

Оператор не задаёт список пользователей. Любой человек начинает личный чат и создаёт свою смету. privateUserContext проверяет корректность Telegram identity и соответствие private chat; группы и аккаунты ботов не обрабатываются. ID используется автоматически в запросах по владельцу сметы, не для допуска. Все history/export/commands/reply/callback остаются scoped по user+chat/draft. Существующие глобальные STT лимиты сохраняются.
